## Coverage and security boundary

The `mcp` workspace provides a **stdio MCP server** backed by the running
application's authenticated HTTP API. It opens no listening port. The MCP client
launches a process bound to an authorized workspace and dedicated API key.
A publisher-bound process can target its verified direct-child newsletters
without a separate process per publication. There is no arbitrary function
invocation, SQL tool, shell tool, credential-decryption tool, or worker/migration
control surface.

Tools are generated from `GET /api/admin/openapi.json`, not from a second,
hand-maintained list. The running server is the contract: new machine API routes
become typed tools on the next MCP process start. `GET /api/admin/operations`
lists methods, paths and required scopes. See [Application API coverage](/guide/api-coverage)
for source ownership and the complete generated function inventory. A function
inventory is a code map, not permission to execute every implementation helper.

Every application feature must have a typed, authenticated MCP operation in the
same change as its browser controls. This includes template authoring and
authorized account/profile/session/team administration. Routine route parity
verification rejects browser-only or hidden product controls.

Account controls use explicit owner-delegated API keys with fresh role and
credential checks, not a fabricated browser session or an arbitrary administrator.
Legacy unowned keys keep their product permissions but cannot acquire personal
account identity. Google login/consent callbacks, provider signatures, public
pixels and signed recipient links retain their protocol authentication; MCP
provides equivalent administrative controls, not bypasses. Debugging, migrations,
raw SQL and private worker primitives are not application features or tools.
Native ingestion covers identify, track, page, screen, group and batch. The
inherited unimplemented alias route has been removed rather than exposed as a
placeholder.

## Create a dedicated key

From an authorized administrator session, use Settings → Admin API Keys for a
read-only key, or the authenticated API with explicit `scopes`:

```http
POST /api/admin-keys/
Content-Type: application/json

{"workspaceId":"YOUR_WORKSPACE_UUID","name":"mcp-reader","scopes":["read"]}
```

Browser authentication and its existing CSRF/Origin rules still apply. An
existing fully privileged bearer key can instead call the equivalent
`POST /api/admin/admin-keys/`. New keys store only a SHA-256 digest and are returned
only at creation; authentication uses constant-time digest comparison. Do not put
real keys in tracked configuration, prompts, URLs or tickets. Duplicate live
names conflict rather than returning an existing secret. Delete a key to revoke
it; deletion takes effect on the next API request, including an already-running
MCP process. Creating a key with a previously revoked name produces a new secret.

API-key credential secrets cannot be changed or deleted through the generic
provider-secret API, including renamed or retyped secrets linked to a key.
Use the dedicated admin-key creation and revocation routes instead. This
boundary applies to browser roles and scoped bearer clients.

New keys default to `read`. Persisted pre-scope keys retain their legacy broad
administrative authority: replace those used by automation with scoped keys.
Existing parent-key access to active child workspaces is preserved; a child key
does not authorize its parent or a sibling.

| Scope | Access |
| --- | --- |
| `read` | Product queries, including POST contact/history queries and template rendering. |
| `write` | Product mutations, ingestion, sends, triggers and workflow actions. Not implied by `read`. |
| `destructive` | Deletes, cancellations and explicit destructive operations. |
| `sensitive` | Explicit sensitive data such as owned raw tracking evidence. |

Credential, key, account and access administration requires **all four scopes**,
not `sensitive` alone. Owner delegation is server-owned: authenticated key creation
binds its creator or inherits the invoking key's owner; request data cannot choose
another identity. Revocation, disabled owners and current workspace roles are
rechecked, including inside account mutations. Last-administrator protections and
tenant boundaries remain intact.

`/api/admin/operations` is authoritative for each route. Grants are enforced on
HTTP requests, not just tool visibility. These are coarse workspace capabilities:
`write` includes template edits and sending. Read access can export contact PII.
Tool access is not permission to send, provision providers or delete user data.

Startup discovery requires the API key's `read` grant even when the process will
perform writes. Provision `read,write` for a normal mutation-capable integration;
the grants remain independently enforced.

### Account controls

The `/api/admin/account` family supports owner profile changes, authorized
workspace preference, browser-session inspection/revocation, team invitations,
roles/removal and permitted account disabling. A key cannot widen its workspace
binding or choose another account. Creating a workspace does not automatically
grant that workspace to the invoking credential.

Machine profiles identify `currentKeyId`, never a fabricated current browser
session. **Logout revokes the invoking API key.** **Revoke others revokes all of
the owner's browser sessions**, because a machine key has no current browser
session. Existing browser controls retain their browser-session semantics.

### Required feature check

Run `yarn check:mcp-parity` for every feature change. It inventories actual
registered routes and authenticated OpenAPI across supported authentication modes,
checks typed machine inputs and scope enforcement, and exercises the stdio
consumer. Hidden routes and new browser-only controls fail the check; only exact
authentication/signed-protocol exceptions have reasons.

The parity harness has no database lifecycle hooks and denies network/database
access. It must be safe to run from a checkout with a real development `.env`.
Add a real MCP consumer scenario for new or changed behavior; route parity alone
does not establish correct business semantics.

## Build and connect

From the repository root with Node.js 20 or later:

```bash
yarn install
yarn workspace mcp build
```

Configure your MCP client using absolute paths (replace placeholders privately):

```json
{
  "mcpServers": {
    "ronin": {
      "command": "node",
      "args": ["/absolute/path/to/dittofeed/packages/mcp/dist/src/index.js"],
      "env": {
        "DITTOFEED_API_URL": "https://your-application.example",
        "DITTOFEED_WORKSPACE_ID": "YOUR_WORKSPACE_UUID",
        "DITTOFEED_API_KEY": "YOUR_DEDICATED_KEY",
        "DITTOFEED_MCP_SCOPES": "read"
      }
    }
  }
}
```

For the combined local Lite preview use `http://localhost:3000`; HTTP is allowed
only for loopback. Non-loopback connections require HTTPS. The configured URL
may include an API deployment prefix, but not credentials, query or fragment.
Redirects are rejected to prevent credential forwarding. No browser cookie is
read or forwarded. No `.env` file is loaded implicitly; inject the key using the
MCP client's private environment or a secret manager.

`DITTOFEED_MCP_SCOPES` is an additional local ceiling, defaulting to `read`.
For an intentionally privileged automation process, explicitly set
`read,write,destructive,sensitive` **and** provision a key with the needed API
grants. Increasing the local ceiling cannot grant authority the API key lacks.
Use separate processes and keys for read-only research and outbound campaigns.

### Configured local OMP client

The `RONIN Development` workspace uses a dedicated owner-delegated credential
with `read,write,destructive,sensitive`. The original
`local-development-readonly` key remains unchanged. The active connection settings
live in the existing ignored root `.env`, protected by owner-only `0600` permissions:
`DITTOFEED_API_URL`, `DITTOFEED_WORKSPACE_ID`, `DITTOFEED_API_KEY` and
`DITTOFEED_MCP_SCOPES`. Never commit them.

The full-control feature preview runs the combined Lite app on
`http://localhost:3005`, sharing development data while leaving the existing
browser preview on port 3000 untouched. The ignored `.omp/mcp.json` launches the
matching compiled bridge from the feature checkout with an explicit
`--env-file` pointing to the original root `.env`; the client JSON contains no
API key. This launch requires Node.js 20.6 or later.

After changing the project launcher, run `/mcp reload` in the existing OMP
session so it rediscovers the configuration; editing the file or restarting only
the daemon's host unit does not reload the session's launch specification.
After rotating a key in `.env`, run `/mcp reconnect ronin-dittofeed` to restart
the server with the current credential. `/mcp test ronin-dittofeed` checks the
registered connection against the live server. A fresh standalone stdio process
does not prove an already-mounted session is using the same configuration.
The configured API must be running. Neither the MCP process nor its client
configuration starts infrastructure or changes browser authentication.

The root `.env` is plaintext protected by filesystem permissions: protect
backups and never paste its contents into a prompt or commit it. Revocation uses
Settings → Admin API Keys or the authenticated key-deletion API; rotate by issuing
a new dedicated key and privately replacing the local credential. Keep read-only
research on the separate reader key instead of widening that credential.


## Tools and resources

Each supported operation gets a stable tool name derived from HTTP method/path,
with a collision-resistant suffix. Tool descriptions contain the method, path
and required scopes. Tool input JSON Schema comes from request schemas:

- `body`: JSON request body, with workspace assigned by the process.
- `newsletterId`: optional top-level selector on native product tools for a
  publisher's direct-child newsletter. The bridge verifies the live relationship
  before applying child scope consistently to headers/query/body. It cannot
  target foreign workspaces; publisher-management tools stay publisher-bound.
- `query`: typed query parameters; nested objects and arrays use the API's `qs`
  encoding.
- `path`: declared URL parameters, encoded individually.
- `headers`: only declared application headers, such as `df-segment-id`.
  Authorization, workspace, cookie, host and proxy headers cannot be supplied.
- CSV upload tools take `file: {filename, contentBase64}` and declared headers.
  No local filesystem path is read. The decoded file is sent as multipart CSV.

For example, find the POST `/api/admin/users/` tool in `tools/list`, then invoke
it with `{"body":{"limit":10}}` plus any required query schema fields. Follow
the returned cursors rather than assuming the first page is the full dataset.
The server fixes `df-workspace-id`; conflicting workspace selectors are rejected.

For publisher/newsletter lifecycle, deliberate cross-publication automations,
managed SendGrid connections, shared-IP budgets and release gates, see
[Ronin multi-newsletter operations](/guide/newsletters).

Tool results contain `{status, contentType, encoding, body}`. JSON remains JSON
text inside `body`; CSV/text are UTF-8, and binary downloads are base64. HTTP
4xx/5xx responses set MCP `isError`. No background retries are performed. Calls
have a 60-second deadline, a 5 MiB serialized request/file bound and a 16 MiB
response bound; larger results fail explicitly rather than silently truncating.
Use direct HTTP for larger exports. Cancellation/deadline does not undo a send
or other mutation already accepted by the server; inspect state before retrying.

`dittofeed://api/openapi` is a read-only MCP resource containing the discovery
contract loaded at startup. Restart the process after changing the API contract
or local scope ceiling. Key revocation and server-side authorization are checked
on every call; the MCP process never caches permission to execute an operation.
A tool may be visible under the local ceiling but rejected by the key's narrower
API grants.

Tool annotations are hints, not authorization or a substitute for client-side
human approval. Contact traits, templates and external content can contain prompt
injection; treat results as untrusted data. Require confirmation in the MCP client
before sends, bulk edits or deletions. Standard input/output is JSON-RPC only;
startup/protocol diagnostics go to stderr without credentials or response bodies.

## Direct HTTP and deployment

Use the same dedicated bearer credential and explicit tenant:

```bash
curl --fail-with-body "$DITTOFEED_API_URL/api/admin/operations" \
  -H "Authorization: Bearer $DITTOFEED_API_KEY" \
  -H "df-workspace-id: $DITTOFEED_WORKSPACE_ID"
```

The MCP bearer guard does not secure an otherwise anonymous browser deployment.
Configure a supported non-anonymous authentication mode (for example
`AUTH_MODE=google` or `single-tenant`) before exposing the application publicly.

Keep the API behind TLS, normal ingress request limits and access controls.
Do not log Authorization headers, private MCP environment configuration, raw
tracking evidence or export bodies. Secure MCP client logs/transcripts: they can
contain contact PII and sensitive operation results. This stdio server is not a
remote OAuth authorization server and does not add a public `/mcp` listener.
Expose neither stdio over an unauthenticated TCP proxy nor the API through an
unrestricted agent execution service.

Email provider acceptance is not delivery. `last_clicked`, `last_opened` and pixel
receipts remain observed, unqualified evidence; MCP does not introduce a human
engagement classifier. Tracking retention, encryption and erasure rules are
unchanged. API keys authorize application work, not changes to those semantics.
